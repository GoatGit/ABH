# ABH 与 Lime Ads 模块详细设计规范

> 规范级别：Normative
>
> 目标成熟度：D2 工程可实现设计；达到 D3 仍需机器契约、代码、测试、压测和演练证据
>
> 开源适用范围：ABH 公共 Package、SDK、Adapter、Pack、CLI、Workbench Extension 和 Distribution
>
> 版本：1.9
>
> 日期：2026-09-07

## 1. 详细设计成熟度

| 等级 | 含义 | 判定标准 |
|---|---|---|
| D0 · 名称 | 只有模块名或能力清单 | 不能用于分工或实现 |
| D1 · 边界 | 已定义定位、职责、主要对象和上下游 | 可讨论架构，不能直接开发 |
| D2 · 工程可实现 | 具备用例、数据所有权、接口、状态引用、时序、并发、失败、安全、SLO 和测试矩阵 | 可以拆任务、建契约和进入实现评审 |
| D3 · 已验证 | D2 设计对应机器 Schema、实现、自动化测试、压测、故障注入和运行证据 | 可以按开放门禁评估生产启用 |

`docs/V1/` 的模块详细设计目标是 D2。文档写有“详细设计”不自动代表 D2；缺少唯一 Owner、主时序、失败收敛或可验证验收中的任一项，都仍按 D1 处理。

## 2. 模块成立条件

模块是一个可独立实现、测试和验收的职责单元。满足以下任一条件即可单独设计：

- 对外提供稳定 Port、Command、Query 或 Event；
- 拥有独立状态、版本或生命周期；
- 对一组数据拥有唯一写入责任；
- 具有独立失败、重试、恢复或安全语义；
- 是用户可识别、可独立完成任务的产品能力。

纯工具函数、展示片段、横切属性和仅为解释而存在的名词不建立模块。模块边界与部署边界正交。

## 3. D2 必备设计内容

### 3.1 系统与领域模块

每份系统或领域模块详细设计必须明确：

1. **定位与非职责**：解决什么问题，哪些责任由上下游承担；
2. **核心用例**：至少覆盖主路径、拒绝路径、恢复路径和治理路径；
3. **依赖与数据所有权**：同步依赖、异步依赖、拥有的表/聚合/索引、只读数据；
4. **契约**：Command、Query、Event、Port/API 的字段、前置条件、返回值、稳定错误码、公共/内部属性和 Stable/Preview/Experimental 稳定等级；
5. **状态**：引用状态唯一规范，写明本模块可提交哪些迁移以及触发证据；
6. **主时序**：至少一条主流程和一条故障/恢复流程，标出事务边界与外部副作用；
7. **一致性与并发**：幂等键、乐观锁、租约、fencing、乱序/重复事件、缓存失效；
8. **失败模型**：错误分类、重试主体、最大重试、降级、人工责任和最终收敛；
9. **安全与隐私**：Tenant/Purpose、授权重验、Secret、字段裁剪、审计和保留；
10. **SLO 与容量**：继承的全局目标、模块预算、背压和容量假设；
11. **可观测性**：Metric、Log、Trace、Audit 的最小字段、告警和 Runbook 入口；
12. **测试与验收矩阵**：用例、并发、故障、安全、契约、回放和性能的可观察断言；
13. **部署与演进**：初始进程归属、公开配置 Schema、迁移兼容、拆分触发条件、自托管和断网行为；
14. **开放问题**：尚无证据的参数或能力必须登记到开放门禁，不能写成已实现事实。

“列出接口名称”不算完成契约设计，“描述会重试”不算完成恢复设计。D2 对工程细节的最低颗粒度如下：

| 设计项 | D2 最低颗粒度 |
|---|---|
| Command | 业务 Payload 必填字段、服务端补全字段、前置条件、幂等 Scope、事务内写入、返回值、事件和稳定错误 |
| Query | Filter、排序、Cursor、权限裁剪、`asOf/watermark/stale`、最大页大小和一致性来源 |
| Event | 触发事务、Aggregate Version、最小 Payload、消费方、顺序/重复/缺口处理和兼容策略 |
| Port | Caller、Implementer、Sync/Async、超时、取消、幂等、一致性、错误与 Trace Span |
| 状态迁移 | 唯一 Owner、Command、起止状态、必要证据、CAS/锁、Outbox 和失败后状态 |
| 外部副作用 | Proposed/Authorized Action 分界、事务提交点、Operation Plan Owner、Dispatch 点、幂等键、Attempt/Receipt、Unknown 查回、补偿和最终收敛 |
| 失败恢复 | 故障发生点、可观察状态、自动处理者、重试上限/禁止重试条件、人工责任和终止条件 |
| 验收 | 给定输入/故障与可以从 API、事件、数据库、Audit 或 UI 观察到的确定断言 |

每份详细设计至少给出一条主时序和一条故障恢复时序。数据存储、纯 Projection 等没有业务 Command 的模块，可以用写入协议与查询时序代替，但必须标明事务、检查点和重放边界。

### 3.2 Agent 模块

Agent 责任文档除上述适用部分外，还必须定义：任务触发、输入 Context Manifest、`AgentTaskContract`、结构化输出 Schema、可用工具及副作用等级、委托规则、验证器、停止/升级条件、记忆读写、评测数据集和禁止泛化边界。Agent 不拥有正式状态或外部执行权。

### 3.3 产品模块

产品模块详细设计必须明确：目标用户与场景、信息架构、页面/组件解剖、主旅程、空/加载/过期/失败/部分成功状态、角色差异、数据 Projection、Mutation/Decision 路径、响应式与无障碍、埋点、性能预算和可用性验收。页面不复制领域状态机，而是使用生成类型映射为业务语言。

### 3.4 Web 技术模块

Web 技术模块必须定义：前后端边界、类型来源、缓存键、失效规则、并发与取消、实时事件顺序、错误呈现、安全裁剪、性能预算、浏览器/设备范围、可访问性门禁和测试层级。

## 4. 文档组织

系统模块文档应覆盖：定位与价值、职责与边界、上下游、核心用例、内部组件、状态与数据、Commands/Queries/Events、Port 或 API、时序、并发与幂等、失败恢复、安全与租户隔离、可观测性、配置、测试和验收。

产品模块文档应覆盖：用户与任务、信息架构、页面和对象、核心旅程、交互与状态、角色和权限、数据来源、异常与恢复、可访问性、分析指标和验收。

Agent 责任文档应覆盖：目标、输入、结构化输出、可用工具、委托关系、上下文与记忆、验证、停止条件、失败处置和评测；Agent 不虚构独立数据库或部署单元。

领域对象文档应覆盖：聚合边界、业务不变量、状态机、字段、命令、事件、查询、权限、并发和保留策略。

为了便于阅读，可合并相邻章节，但不能省略 D2 内容。共享 Envelope、错误码、事件元数据和 SLO 只在公共规范定义；模块文档引用公共规范并补充本模块特有语义，避免复制后漂移。

## 5. 契约规则

1. JSON 对外字段统一使用 `camelCase`；时间统一为带时区的 ISO 8601；金额、汇率的字符串表示、单位和精度统一引用《系统边界与技术基线》第 3.1 节，模块声明具体字段的舍入与范围约束。
2. Command Envelope 必须携带 `idempotencyKey` 和必要的 `expectedVersion`；其服务端签发的 `RequestContext` 携带 `actingOrganizationId`、`resourceOrganizationId`、`actor`、`purposeOfUse` 和 `correlationId`。`RequestContext` 只表达可信请求身份，`AuthorizedRequestContext` 必须引用针对明确 Target 生成的 Authorization Snapshot；不得把 Envelope 字段复制进 Context 形成第二来源。
3. 租户资源的 Repository 必须在边界接收 `TenantContext`，查询不可由上层临时拼接租户条件。
4. 正式写入使用乐观锁；异步发布使用 Transactional Outbox；外部副作用使用可持久 Action。
5. DTO 与 Schema 只有一个权威来源；第三方字段在 Adapter 边界映射。
6. 错误分类、稳定错误码及 HTTP/Tool 映射完整引用通用契约的 Error Registry；模块只能增加已登记 Owner 的特有错误，不得缩减或另造公共分类。
7. 通用 Command、Query、Event、错误与分页契约统一引用下游《通用应用契约与错误模型》；目标产物与放行条件见第 13 章。
8. 所有 Port 都要声明调用方、实现方、同步/异步、幂等语义、超时预算和取消传播。
9. 示例字段只表达设计意图；进入实现前必须落到机器 Contract Package，并由 CI 验证文档引用的契约版本存在。
10. 外部副作用统一遵循 [ABH 第 8.1 节](Agentic-Business-Harness总体设计.md#81-可信执行链)的 Preflight、策略分层、版本分配和授权协议。D2 必须具体标注 RequestContext 输入、Action 专属 Snapshot、全部 Ledger 预留、Authorized 提交及 Dispatch 重验的事务边界；Authorization Resolver 签发授权上下文，Action Engine 提交 Action。上游 Invocation/Tool Snapshot 仅作来源证据，不能代替本 Action 的授权。
11. Operation Controller 是 Operation Plan 的唯一 Owner；Domain Owner 声明副作用要求，Action Engine 拥有父 Action 与子 Operation 汇总规则，Connector 只执行已确定的 Operation。Action 幂等键去重业务意图，Operation 键稳定派生，同一 Operation 的 Attempt 复用同一 Provider 幂等键；无原生幂等时详细设计必须给出稳定外部标记、查前写/写后查、零/单/多匹配处置和自动写入降级。补偿作为引用原 Operation 的新 Action，不改写历史 Receipt。
12. Mission Controller 唯一发起 Run 创建/唤醒，Run Orchestrator 唯一提交 Run 创建、启动快照、Task Graph 并调度 Invocation，Coordinating Agent 只提出计划、委托和 Graph Patch。Capability Release Controller 唯一提交 Release/Assignment；版本固定、撤回及重验引用 ABH 规范。Canary 详细设计必须声明分配单元、稳定分桶键、持久化与重试不重分组规则。
13. Gate Artifact 只能引用候选运行前已冻结、由独立规则选择的 Evaluation Profile（Suite/Dataset/Evaluator/Metric/Threshold）。生产 Capability Release 只记录 `gateArtifactRef/evaluationProfileRef` 作为证明，不将评测集作为运行行为资产分配；Evaluation Profile 自身变更使用独立黄金/事故/对抗集和新旧双跑验证。

## 6. 状态与事实规则

- Agent 输出是提案，领域 Repository 中已提交的对象才是业务事实。
- 外部平台事实以最近一次可追溯同步或回执为准，并保留 `sourceRef` 与 `observedAt`。
- Workbench 使用 Projection，不直接读取 Agent 内部事件拼装业务事实。
- 状态迁移必须由唯一 Owner 模块提交，其他模块只能发 Command 或订阅 Event。
- Memory、Knowledge、Result 和审计记录按各自用途保存，不能互相代替。
- Mission Memory 由 Agentic Core Memory Owner 提交；Domain/Customer Memory、Result 和 Knowledge 由对应 Domain Owner 提交；Evaluation & Learning 拥有 Learning Signal/Case、Capability Candidate 和 Gate Artifact；Capability Release Controller 拥有 Release/Assignment。模块详细设计必须指向其中一个 Owner，不能使用“Learning Plane”作为模糊写入者。
- 所有跨模块持久状态枚举引用下游《状态与执行契约规范》；Decision、Grant、Budget/Commitment、Action 与 Operation 引用下游《责任、授权与执行链规范》，模块文档不得另立不同真相。
- 延迟、可用性、数据新鲜度、RPO/RTO、容量和拆分门槛引用下游《NFR、SLO 与容量模型》；在其形成前，以[系统边界与技术基线第 9.1 节](系统边界与技术基线.md#91-初始-nfr-与容量验收包络)为最低包络，局部模块只能定义更严格的目标并说明适用 Scope。
- Error 与 Outcome 是正交维度：Error Registry 描述失败原因和处置；`Unknown` 描述外部副作用尚无法证实成功或失败。模块不得把 `Unknown Outcome` 编为普通可重试错误，也不得在对账前盲重试可能已生效的 Operation。

## 7. 安全与 AI 约束

- Agentic Core 内只有 Pi Agent Runtime Adapter 可以启动模型—工具循环。
- 所有模型请求经 Trusted Runtime Model Gateway；所有工具经 Tool Gateway；所有外部写入经 Action Engine。
- Human Gateway 记录人类责任事实，Trusted Runtime 计算权限，二者不承担营销生产。
- 默认按 Organization、Workspace、Brand、Mission 和数据用途隔离；客户数据不得默认用于跨客户训练或 Benchmark。
- 高影响操作必须保留输入版本、策略判定、人工责任、执行回执和可追溯 Evidence。
- Audit 详细设计必须区分“可追溯、限权追加”与已启用签名摘要/WORM 后的“篡改可见”；不得在没有密码学和外部存证的情况下声明不可抵赖。普通应用角色禁止更新/删除 Audit，保留或法定删除必须经受审计 Maintenance Command。

## 8. SLO 与容量写法

- 模块从全局《NFR、SLO 与容量模型》继承端到端目标，并给出自身所占预算；
- Provider 响应目标和 Lime Ads Internal SLO 分开，外部超时不能伪装成内部成功；
- 容量写明 Scope、稳态、突发、背压和降级顺序，不用无来源的“高并发”“低延迟”；
- 安全关键路径必须说明超限时 fail closed、降级或转 Unknown 的选择。

## 9. 验收写法

验收条件必须是可观察结果，至少覆盖：主路径、拒绝路径、并发冲突、依赖失败、租户隔离、审计完整性和恢复路径。禁止以“代码已完成”“页面已存在”作为验收标准。

推荐使用测试矩阵：

| 类别 | 场景 | 输入/故障 | 可观察断言 |
|---|---|---|---|
| Contract | 合法请求与版本兼容 | 固定 Schema | 返回字段、事件和错误码完全匹配 |
| Concurrency | 重复、乱序、并发修改 | 相同幂等键/旧版本 | 无重复副作用且冲突可恢复 |
| Failure | 依赖超时、Worker 崩溃 | 故障注入 | 状态显式、可重放、不误报成功 |
| Security | 跨租户、撤权、越权 | 无效上下文 | fail closed 并形成最小 Audit |
| SLO | 稳态与突发 | 设计容量 | 达到模块预算且触发正确背压 |

## 10. 文档完成门禁

模块进入“D2 完成”前，由设计评审逐项回答以下问题；任一答案只能从常识推断而不能从本文或权威引用直接找到时，仍按 D1 处理：

1. 调用方应发送哪些字段，服务端会忽略或重算哪些字段？
2. 哪个模块、哪张表、哪个事务提交正式事实和 Outbox？
3. 重复请求、并发相反请求和迟到事件分别得到什么结果？
4. 在事务提交前、提交后但发布前、外部已接收但未回执三个故障点如何恢复？
5. 调用方如何区分拒绝、冲突、暂时失败、永久失败和 Unknown Outcome？
6. 撤权、Scope 切换、数据用途变更或删除如何传播到缓存、Run、Binding、Index 和派生数据？
7. 设计容量下的延迟、队列、Payload 和单聚合大小上限是什么，超限后保护什么、舍弃什么？
8. 测试能观察到哪些状态、事件、回执、Audit 或用户行为来证明设计成立？
9. 哪些符号和扩展点是 Stable/Preview/Experimental/Internal，对应的 SemVer 和弃用策略是什么？
10. 第三方能否仅用公开 SDK、公开测试和公开文档独立实现、运行和诊断该模块？
11. 哪些设计参数已由证据冻结，哪些仍是待校准假设，且后者是否有实名 Owner、截止门禁和失败后安全默认？

详细设计允许引用公共 Envelope、状态和 NFR，但不得用“参考公共规范”省略本模块的业务 Payload、前置条件、事务效果和特有错误。

## 11. 防止过度设计

每份文档结尾说明模块为何独立、哪些职责刻意留在上游或下游，以及哪些能力暂不抽象。若两个候选模块没有不同的状态、接口或失败语义，应合并为同一模块的内部组件。

模块设计服务于框架维护者，接入者只阅读其使用能力的 SDK/配置合同。实现必须支持构建期按需装配：未启用能力不产生必需依赖、占位对象、后台订阅或维护作业；已有未决责任仍按安全停用协议处理。首条交付按 [工程路线](../10-ABH详细设计/62-工程实施与验收门禁.md)先验证独立 Action，再验证 Mission/Agent，不把全部详细设计或参考 Workbench 作为接入前置。

实现复用遵循 [ABH 第 4.5 节](Agentic-Business-Harness总体设计.md#45-abh-自研边界)。模块的 Owner 表达业务契约与验收责任，不能据此推导“整模块自研”。每个模块实现评审须给出以下最小记录，写在既有设计/实现 PR 中，不另建选型平台：

| 必答项 | 判定要求 |
|---|---|
| 复用内容 | 已选组件、公开入口、固定版本与实际承担的能力；继承公共基线的部分直接引用 |
| 必要补缺 | 现有实现不能满足的具体合同/失败用例，自研范围和可观察验收结果 |
| 总体成本 | 集成、运维、升级、安全维护和退出影响；不能仅比较初次编码量 |
| 退出方式 | 上游实现何种能力后可删除补缺，以及状态、数据与旧运行如何迁移 |

已有依赖足够时直接复用，不为完成比较再引入候选组件。通用问题优先通过配置、公开扩展和上游贡献解决；薄适配与必要业务实现可继续交付。新增依赖、长期 fork 或重复 Loop/队列/授权/存储必须在本模块评审中解释，生产门禁和安全不变量不因复用而豁免。代码量、依赖数量和自研比例只作维护参考，不设鼓励堆库或代码搬运的比例目标。

## 12. 开源模块的附加设计契约

### 12.1 公共 API 和扩展边界

每个发布到 `@abh/*` 的 Package 或通过 Pack/Extension 暴露的模块，详细设计必须额外定义：

1. Package 名、Owner、许可证、发行制品和支持等级；
2. `package.json#exports` 的公共入口和禁止导入的 `internal` 路径；
3. 所有对外符号、Schema、Event、CLI Flag 和配置项的 Stable/Preview/Experimental/Internal 标签；
4. 允许的扩展输入、生命周期、并发语义、错误隔离、资源上限和不得绕过的 Owner；
5. 一个仅使用公共入口的最小可运行示例；
6. 与稳定级别匹配的编译、运行、契约和升级兼容矩阵：Stable 1.x 默认验证当前与最多两个已实际发布的前序次版本组合，Preview 默认当前与一个已发布前序次版本，Experimental 与 0.x 只承诺 `compatibility.yaml` 公布的组合；初次发布不为不存在的历史版本制造虚假兼容证据；
7. 弃用时间表、替代 API、Codemod/迁移方法和回滚条件；
8. Pack/Extension 必须声明 Declarative、TrustedCode 或 Isolated Trust Mode，以及 Data、Purpose、Command、Tool、Network、Secret 和资源权限 Manifest；CTK/签名不得被描述为安全审计的替代。

ABH Core 的详细设计必须使用领域中立语言。Marketing、Procurement 或其他行业实例可出现在 Pack 文档和测试 Fixture，不得成为 Core 类型、默认 Policy、数据库结构或错误码。

### 12.2 开源可操作性

每个运行模块还必须定义：

- 所有配置项的 Schema、默认值、密级、重载/重启语义和未配置时的失败方式；
- `abh doctor` 的健康检查、故障码、用户可执行的修复指令和 Runbook 链接；
- 离线、代理、限制网络出口、自签证书、多架构镜像和只读文件系统下的行为；
- 数据导出、导入、备份、恢复、清理和不可逆迁移前的安全点；
- 该模块在 `abh-core`、`abh-full` 和 `abh-dev` 的启用状态，以及开发 Fake 在生产 Profile 的强制拒绝规则；
- 任何遥测或网络出口的主机、目的、Payload 类别、默认状态和关闭方法；ABH 项目遥测必须默认关闭。

### 12.3 公开测试与供应链

| 设计项 | 必须明确的内容 |
|---|---|
| Contract Test | 使用的 CTK、Fixture、符合性声明范围和可签名结果 |
| 覆盖率 | 公共包行覆盖 ≥ 85%、分支覆盖 ≥ 80%；安全关键可达分支 100% |
| 深度测试 | 适用的 Property、Fuzz、Mutation、Replay、故障注入和升级测试 |
| 依赖许可 | SPDX ID、来源、通知/归属、发行方式、混合许可边界和退出方案 |
| 安全 | Threat Model、CodeQL/OSV/Secret/Image 扫描、漏洞响应 Owner 和修复 SLO |
| 制品 | SPDX/CycloneDX SBOM、Checksum、SLSA Provenance、Cosign Signature 和可复现构建说明 |
| 文档 | API Reference、最小示例、How-to、故障排除、Release Notes 和 Migration Guide |

正式模块不得依赖私有测试、私有模型账号或不可获得的外部数据才能完成合并和发布。供应商真实账号测试可作为附加冒烟证据，公开模拟对端和 Fixture 必须能独立证明契约、错误和恢复语义。

### 12.4 D3 开源验证

开源模块达到 D3 还需要：公共 API 和文档已发布；CTK 可在 clean-room 环境复现；相应稳定级别的兼容矩阵已通过；升级、回滚和导出路径有运行证据；发行制品、SBOM、Provenance 和签名可从公开 Source Tag 验证。官方 Supported 等级还需在 `MAINTAINERS.md` 指定 Owner 和安全响应者。

## 13. 下游工程规范与实现放行

`00-总体设计` 冻结架构不变量、产品语义、运行 Profile、Pack 边界和详细设计质量门禁。以下产物负责把它们转换为可生成、可测试的实现契约；目标路径是文档身份，不因路径存在就自动达到 D2/D3：

| 必需产物 | 目标路径 | 唯一责任 | 最早放行点 |
|---|---|---|---|
| 状态与执行契约规范 | [ABH 状态规范](../10-ABH详细设计/02-状态与执行契约规范.md) | 状态枚举、迁移、Owner、Outcome 与代码生成映射；领域对象由 Pack 自有契约定义 | 任何持久状态实现前 |
| 责任、授权与执行链规范 | [ABH 授权执行链](../10-ABH详细设计/03-责任授权与执行链规范.md) | Decision—Grant—Reservation/Commitment—Action—Operation 一致性 | M0 模拟 Action 前 |
| 通用应用契约与错误模型 | [公共契约](../10-ABH详细设计/01-公共契约与错误模型.md) | Envelope、Context、Error Registry、幂等与兼容 | 第一个跨模块 API/Job 前 |
| Contract Package 设计与机器制品 | [Contract Package](../10-ABH详细设计/05-Contract-Package与一致性检查.md)、`packages/contracts` | Schema 单一来源、生成目标与一致性 CI | 状态/API/Event 类型落码前 |
| NFR、SLO 与容量模型 | [NFR 与容量](../10-ABH详细设计/04-NFR与容量模型.md) | 端到端预算、负载、RPO/RTO、背压与拆分阈值 | M1 生产资格评审前 |
| 首条工程纵向交付路线 | [工程实施与验收](../10-ABH详细设计/62-工程实施与验收门禁.md) | 一条端到端切片的依赖、验收和停机线 | M0 任务拆分前 |
| 子系统与模块 D2 设计 | [ABH 模块地图](../10-ABH详细设计/00-模块地图与阅读指南.md) | 各模块 Payload、事务、失败、安全、SLO 和测试矩阵 | 对应模块编码前 |
| 开放问题与生产门禁 | [开放验证门禁](../10-ABH详细设计/62-工程实施与验收门禁.md#4-开放验证门禁) | 证据、责任角色、截止条件、实际责任人绑定与验证方式 | M1 生产写入前 |

放行顺序固定为：架构基线 → 机器契约 → D2 模块设计 → Contract/CTK 测试 → 实现与故障注入 → 生产资格。缺失产物、重复状态真相、未定 Owner 或 CI 无法证明一致时，只允许继续完善设计和 M0 隔离实验，不得以 UI 演示、Agent 输出质量或人工兜底替代生产写入门禁。
