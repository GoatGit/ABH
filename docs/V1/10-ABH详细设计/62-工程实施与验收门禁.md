# ABH 工程实施与验收门禁

> 版本：1.4 · Owner：Core / Release Maintainers
>
> 本文选择实施依赖与证据，不改变 ABH 终态设计或 Lime Ads Phase；未实现能力保持关闭。

## 1. 首条通用纵向闭环

~~~text
一个 Organization + 合法 Responsibility Principal
→ 现有业务输入 + 一个独立 Action 提案
→ 固定 Action 执行版本与不可变 Plan
→ 一个必要 Decision + 有界 Service Grant / ExecutionAuthority
→ 一个 Fake Connector Action / Operation
→ Receipt / Reconciliation
→ SDK 查询结果 + 标准数据导出
~~~

hello-business 先演示“审批并发布一份已有内部简报”；随后通过 Pi Adapter 接入 Pi Agent 开源组件，在同一闭环前增加 `Mission → 固定 Workflow → Pi Agent 执行 Invocation → 候选 → Verification`。Pi Agent 提供模型—工具循环，Pi Adapter 是 ABH 的合同/Gateway 适配层。Fake 外部系统支持创建、查询、暂停和故障注入，没有真实花费或秘密。两条路径使用同一 Action/授权/对账实现；测试 Actor 与业务证据如实记录来源。

独立 Action Fixture 先配置一个组织、明确提案人/审批人、受限执行 Service、单席位审批规则、静态执行 Release 和有限 Ledger。提案时只有准备权限；批准后 Control 以同一 effectKey 创建 Service Grant/Action 绑定 ExecutionAuthority，再由 T1 授权派发。Fixture 不建立 Mission/Run/Invocation，不把用户 Session 或 Worker 数据库身份当作执行委托。恢复用原 pinSet、Plan 和 Effect Receipt；版本、主体与撤销负例按 21/30/28 的具体合同冻结到 M0-A Fixture。

首次闭环通过生成的 SDK 示例完成人类确认和结果查询，Workbench 单独按启用能力验收；学习捕获不阻塞本闭环。该 Fixture 证明公共协议，不能充当行业业务价值证据。

Marketing 首条真实切片继承其总体设计第 16.1 节；本批先实现通用框架详细设计，不将营销对象写入 Core。

## 2. 实施依赖与验收批次

| 批次 | 实现范围 | 进入条件 | 退出证据 |
|---|---|---|---|
| M0-A 契约 | 首闭环 Schema（含 Authority/PinSet/TenantContext）、State/Error Registry、配置与 Contract Generator | 本组设计评审一致 | 生成/兼容/状态组合及三项补充合同 Fixture 可重复；后续能力复用同一生成链 |
| M0-B 正式事实 | Identity/Fake、Control/ExecutionAuthority、RLS/Owner UoW、Audit/Outbox、Ledger、静态 Pack/Release 配置与公开客户端 | M0-A / G01 | 实际 runtime 角色下租户/CAS/重复/崩溃测试通过，无占位 Mission/Workspace |
| M0-C 受控动作 | Responsibility/Decision、Action/Operation/对账、SDK 示例与标准导出 | M0-B | 不装 Pi Agent/web/学习的独立 Action 完成正常/拒绝/Unknown/恢复 E2E |
| M0-D Pi Agent 接入 | Mission/Run、Definitions、Context、Pi Adapter 接入 Pi Agent 开源组件、Fake Model Adapter、Tool、Verification | M0-C | 真实 Pi Agent 循环经 Gateway 产出候选并进入同一 Action 闭环；适配、取消与恢复 CTK 通过，无供应商旁路 |
| M1 受控写入 | 一个 Domain/Connector、生产身份/Secret、独立 Worker、恢复 | M0-D + 独立安全审查 | 真实低影响写入、权限撤销、对账与用户理解证据 |
| M2 有限经营 | 有限负债、真实数据、学习归因与独立离线评测 | 领域上界与统计/数据合同有效 | 并发预算/尾差、质量、成本与人工投入达标 |
| M3 规模学习 | Canary/Release、必要基础设施增强 | 冻结对照及量化门禁 | 分配可重放、停止/回滚、安全与单位成本可验证 |

同一模块按能力启用逐渐增强，不要求先实现全部终态模块再验证闭环。M0 不部署学习任务、独立权限服务、插件市场或多 Agent 群。M0 完整框架验收覆盖 C、D 两条路径；只接入 Action 的应用仅启用并验证 C 所需能力。Workbench 用自己的 CTK/任务式 E2E 验收，领域产品选择它时须完成对应页面，不成为所有接入者的依赖。

## 3. 模块实现完成条件

每个模块需要：公开 Schema/状态/错误/配置、Owner 数据与迁移、主/恢复时序、契约测试、负面安全测试、必要故障注入、对应 CLI 诊断、文档与运行证据。文档存在只说明设计输入存在；D3 必须有代码与报告链接。

实现任务先标明“复用配置、薄适配、必要业务补缺”及已选上游入口；按 [模块设计规范第 11 节](../00-总体设计/模块详细设计规范.md#11-防止过度设计)给出缺口和退出条件。通用能力已有合适开源实现却继续自研的任务，需要具体合同/总成本依据；模块数量和自研代码量不作为进度或竞争力指标。

每批验收复核本批新增/修改的依赖、补丁和重复机制，比较接入工时、运行开销、维护负担与业务正确性。上游替代通过同等 CTK、恢复与性能验证后，删除旧实现并同步锁文件/文档；未通过则保留有证据的最小补缺。沿用现有评审和发行门禁，不新增常驻服务或并行框架，也不因持续选型阻塞已确定的纵向闭环。

批准生产写入按 Scope/Connector/Action Type 单独记录，不能因 Core CTK 通过就给全部领域开权限。未通过的能力配置启动失败或明确 unavailable，不能提供假实现返回成功。

上述 Maintainer 为仓库责任角色，不虚构已到岗人员；每个批次启动前须在 CODEOWNERS/维护登记中绑定真实执行与审查负责人。未绑定角色不能签署该门禁通过。

## 5. 验证矩阵

所有路径均包括主用例、缺权限、旧版本、重复、乱序、事务提交前后崩溃、Provider 已接受但响应丢失、用途撤回、并发资源争用和恢复。安全核心必须观察实际外部 Fake 状态、账本与 Audit，而不是仅测试响应码。

数据/报告保留 commit、Contract Version、Profile、依赖锁摘要、随机 seed、环境、失败例和已知限制。基准提前冻结；测试失败不能事后放宽门槛。真实业务价值与 SOTA 比较在对应 Domain 评测协议中验证，工程闭环成功不替代经营成效。

以下跨模块断言是相应批次的必需证据，不能只由单模块单元测试代替：

| 协议 | 截止门禁 | 必须观察的结果 |
|---|---|---|
| Invocation 装配 | M0-D | Created 身份 → TaskSpec → Manifest/Binding → 完整合同无循环依赖；中断可恢复 |
| 状态关闭与触发 | M0-D | Queued/Verifying 可取消，Blocked 上暂停不会误恢复；有效待处理 Trigger 不丢失 |
| 独立复评 | M0-D | 同输入可新建复评，重复同请求只返回原结果；缓存不跨租户/验收规则 |
| 独立执行委托 | M0-C | 合法提案可等待 Authority；全部批准后才创建有限 Service Grant/Authority；重复/崩溃不重签，错主体/用途/绑定和撤销阻断新 Permit |
| Run/Action 版本固定 | M0-C，D 扩展 Run | 无 Run 可固定完整 pinSet；固定后新发布/重启仍使用原 Connector/Plan；继承 Run 不重选，缺槽位和异摘要不能留下部分集合 |
| 数据库租户边界 | M0-B | 漏应用租户条件仍隔离；A/B 连接复用、异常回滚、非法角色切换均不越界；合法跨组织核验可用，同一 T1/T2 仍原子 |
| 计划与资源授权 | M0-C | 非空 Plan 先于 T1 固定；零派发重授权和长计划 Snapshot 续签不双占资源，持续原负债保留 |
| 多方责任 | 对应路由能力启用前 | 默认单席位审批；启用 ANY/ALL 时验证条件求交，全部必需批准完成前 Grant 数量为零 |
| 持久等待与扇出 | M0-C/D | C 验证 Action/Decision，D 扩展 Run 等待；信号早到、部分投递、旧 Worker 回执均可恢复 |
| 模型/工具出站 | M0-D | 同 callId 只派发一次，逐轮来源撤回阻断新发送，费用不双扣 |
| 持久执行身份 | M0-C/D | C 验证 Session 到期后独立委托；D 验证提案 Invocation 完成后合法 Service 可继续；撤销 Authority 后排队 Action 不派发 |
| Unknown 与止损 | M1 | 受控 safetyStop 可止损且原未知仍对账；旧请求迟到后重新确认停止 |
| 账本计量 | M0/M2 对应能力前 | capacity 可归还；跨期/超额/退款不制造虚假可用额度 |
| Shadow / Canary | M3 | Shadow 无生产写入；Canary 唯一规则解析基线/候选，版本与分组可重放 |

易用性同时验收实际依赖与人工操作：全新环境仅启动 server + PostgreSQL，独立 Action 无可选运行包；一个业务源码文件、一份配置、零手写基础 Adapter，主动操作 ≤ 15 分钟，下载/构建等待另计。再验证已有前端能完成审批、用普通 JSON/JSONL 工具读取导出、未决责任阻止不安全卸载。上述指标是待实现目标，不能用生成文件数或演示视频代替 clean-room 证据。
