# ABH 责任、授权与执行链规范

> 版本：1.3 · 规范性设计源 · Owner：Control / Human Gateway / Action / Ledger Maintainers
>
> 依赖：[公共契约](01-公共契约与错误模型.md)、[状态规范](02-状态与执行契约规范.md)

## 1. 控制权

Human Gateway 提交 Decision；Control 提交 Grant、MissionAuthority、ExecutionAuthority、Policy Evaluation 与 Authorization Snapshot；Ledger 提交资源预留与 Usage；Action Engine 提交 Action；Operation Controller 提交 Plan/Operation/Attempt/Receipt。调用关系不转移写入所有权。

Product Responsibility 表达谁应负责，Grant 表达能做什么。Human 批准同时要求有效责任与审批 Grant；AgentInvocation 依赖自身 Principal 和 MissionAuthority；后台 Service 的独立执行/查回依赖已登记 ExecutionAuthority。无副作用准备工作校验来源 Command 与当前有限准备权限，不借准备资格派发。ExternalPlatform 只可提交已验证外部观察，不能审批或申请新的媒体写入。

持久 Action 区分 proposedBy 与 executionPrincipalRef：前者保留提出意图的 Invocation/Human/Service，后者是当前实际执行的有限 Service Principal，并须由 MissionAuthority/ExecutionAuthority 显式覆盖。T1/T2 按后者及其权限链授权，sourceCommand/Invocation 作为来源证据单独校验；不借 Worker 的部署身份继承提案人的全部权限。原 Invocation 正常完成或用户 Session 到期不使合法长期委托自动失效，撤销对应 Authority/用途或取消关联 Mission 则阻断新派发。独立 Action 无 Mission 时使用明确 ExecutionAuthority，不创建占位 Invocation 或继承外部 Agent 的自报权限。

## 2. Preflight 输入与版本

Preflight 分为无副作用准备和原子授权两个连续阶段。准备输入为 `actionRef, targetRefs, inputVersionRefs, sourceCommandRef, completionPolicyRef` 与当前 RequestContext；先验证准备资格，由 Release Owner 固定或回读 pinSet，再由 Operation Controller 编译/登记 Plan。此阶段不要求尚未签发的 Action Snapshot，也不要求先存在 Plan。

进入 T1 时在上述输入上增加必填 `pinSetRef/digest, planRef/digest, authorityRefs, resourceRequirements`；Payload 摘要绑定批准内容，客户端不能传 allow=true 或任意已签发 Snapshot 替代检查。独立 Action 的 ExecutionAuthority 由 Control 按[授权设计第 2.1 节](21-Authorization与Policy详细设计.md#21-独立-action-的-executionauthority)签发；缺少时停在 Validated，等待完整 Decision Effect 或合法预授权。

Run 启动选择精确 Capability Assignment，来源 Run 的 Action 继承其 pinSet；无来源 Run 的 Action 首次 Preflight 以自身为固定主体。唯一写入/恢复合同见 [Release 第 4.1 节](30-Capability-Release详细设计.md#41-run-与独立-action-的固定协议)。Scope 优先级及冲突拒绝沿用 ABH 总体设计第 8.1 节；同级多个匹配拒绝，不能“选更新的”。

长期运行保存 `MissionAuthorityRef`，不保存人类 Session Token。每次唤醒重新取得身份、用途、Epoch 与 Grant；撤销原人类 Session 不必自动撤销合法长期委托，但撤销 Grant、委托主体或 MissionAuthority 必须阻断后续运行。

## 3. V1 原子授权事务

V1 所有权威权限、预算和状态位于同一 PostgreSQL；不使用外部账本 Saga。API 可在事务前进行重计算和 OPA 预评估，事务内必须重验参与判断的版本。

~~~text
T0: persist Proposed Action + command receipt + audit + outbox
preparation transactions: domain validation / persist complete pin set / compile and register immutable operation plan
before T1: resolve existing authority or consume complete Decision Effect; prepare policy input
T1:
  lock control fence rows in canonical order
  revalidate actor / tenant / scope / purpose / grants / effective policy / assignment / versions
  verify pinned capability set and registered plan digests / connection scopes / resource upper bounds
  lock resource fence rows in canonical order
  lock required ledgers in canonical order
  reserve all requirements or rollback all
  insert policy evaluation + action-specific authorization snapshot
  Action Engine CAS Validated -> Authorized
  insert audit + outbox + command receipt
COMMIT
Worker wakes from committed outbox
~~~

锁顺序统一为 `tenant/scope control fences → resource fences → ledgers → owner aggregate`，各类均按注册 canonicalLockKey 字典序；聚合键含 Owner/type/id，模块不能自定另一排序。授权 Snapshot 不持有长期事务锁，保存 `checkedVersions, checkedEpochs, payloadDigest, pinSetRef/digest, planDigest, authorityRefs, requirementRefs, policyRefs, assignmentRefs, validUntil`。

T1 失败时全部回滚，Action 保持 Validated。模型、网络 Provider、IdP 远程请求不得放在该事务中；认证输入先验证，实时撤销与 Policy 输入从本地权威记录读取。

## 4. Dispatch 边界与撤权竞争

Operation Controller 在持久记录的 Dispatch 前开启短事务 T2：取得与撤权相同的控制 fence，重验 Snapshot、当前 Mandatory Policy、固定 Behavior Policy、Grant、限额、Stop Epoch 和目标前置条件；保存有唯一序号的 Dispatch Permit、资源 Fencing Token 与 Attempt，随后提交。

首个 Permit 与父 Action 的 Authorized → Executing 在同一应用事务提交，由 Action Engine 执行自己的 CAS，Operation Controller 写 Permit/Attempt；两者不跨 Owner 直接改表。取消操作使用相同控制/资源 fence 和 Action CAS，防止存在已提交 Permit 而父 Action 仍被按“零派发”取消。

Permit 必须绑定一个 Operation/Attempt、Connector 版本、payloadDigest、有效期及 Worker 租约。Worker 在出口调用前核对 Permit 和当前 fencing/stop 信息；超出内部最大派发间隔 5 秒必须重新申请，不能复用旧 Permit。

短时 Snapshot 过期先进入 Action Owner 的 RefreshActionAuthorization，按当前长期权限和未变 Plan 重签并复用既有资源责任，不能对已部分执行的 Action 整体重复预留。没有有效新快照不得发 Permit；已存在 Permit 按在途规则处理，不能以“续签”直接替换 Attempt。

撤权先提交则新 Permit 失败；Permit 先提交则该调用按“在途”管理。数据库与远端 HTTP 无法原子提交，撤权不能保证回收已越过出口的请求；系统在 SLO 内阻断尚未发出的请求，并对在途请求查回、必要时发新止损/补偿 Action。Lease 过期不证明原调用未发生。

默认每个资源并发键只允许一个可能产生效果的未决 Operation；Unknown 占用该键直至查回或有平台可验证 fencing 证据。只读对账与安全暂停使用专门能力和策略，不受普通生成队列拥堵影响。

为避免 Unknown 阻塞止损，Connector 可登记作用于已知 externalId、只降低风险且可验证的 safetyStop 能力。它由独立安全 Action 在同一资源 fence 下受理，冻结普通写入并登记与旧未决项的关系；仅免除“普通未决项占位”冲突，不绕过身份、用途、Policy、费用或 Permit。旧 Unknown 仍占位和对账；旧在途扩张可能覆盖暂停时，必须再次确认/补发安全暂停，不能以第一次暂停回执宣布资源稳定停止。未知创建没有可定位 externalId、或无法证明止损单调性时保持冻结并升级 Exception。

## 5. Decision 到执行

1. Action 缺少责任时创建冻结内容的 Responsibility Request，Action 停在 Validated。
2. Human Gateway 对每个 Slot 保存责任、对象版本、推荐/备选、影响上界、Evidence、到期时间和 Decision。
3. 所有必需 Slot 的 Approved 只形成正式责任依据；Control 再按版本和职责分离创建 Grant/Authority。
4. Action T1 引用这些记录并预留资源；通过后才可 Authorized。
5. 内容、影响、对象版本或必需责任链改变时原批准不能复用；创建新 Proposal/Decision 或重验仍然覆盖的预授权。

独立 Action 的正常首次顺序为：提案及受信执行 Service 绑定 → Validated → 固定执行版本/Plan → Decision → Control 创建有限 Service Grant 和 Action 绑定 ExecutionAuthority → Action Owner 在 T1 绑定 Authority、预留并 Authorized。已存在合法 Scope 预授权时复用其 ExecutionAuthority；准备/提案权限与执行权限分别验证，不为缺失执行 Authority 拒绝保存一个合法待批提案。

跨组织批准分别保存 actingOrganizationId、resourceOrganizationId、Workspace 与责任类型；代理关系属于 Domain Pack 模板，Core 不内置品牌/代理商的隐式信任。

## 6. 暂停、取消、失败与补偿

| 触发 | 未派发 | 已派发 / Unknown |
|---|---|---|
| Mission 暂停/取消 | 提升 stopEpoch，停止新 Invocation，取消/冻结相关待执行 Operation | 保持正式记录；独立 Service 继续查回与止损 |
| Grant / Purpose 撤销 | Snapshot 失效，拒绝新 Permit | 仅执行合法的合规留存、查询或紧急止损；不得借对账扩张用途 |
| 对象版本变化 | 重新规划或新 Action | 保存原输入和外部观察；按补偿意图另起 Action |
| Ledger 超额 | 拒绝新增预留/扩量 | 实际 Usage 如实追加，可出现显式欠额，冻结扩量 |
| Worker 崩溃 | Permit 未生成可安全再次唤醒 | 有 Permit 而效果不明先查回，禁止按队列重试重发 |
| 对账超窗 | 不新增依赖写入 | Exception + Unknown 继续保留，不能靠超时释放责任 |

补偿使用当前授权和新资源预留，引用具体原 Operation。回滚配置、暂停或退款在业务上可能不是精确逆操作；Connector/Domain 必须声明可逆性和残余影响。

## 7. 留痕、保留与验收

Trust Envelope 是只读投影：关联 Decision、Grant、Snapshot、两类 Policy、Release/Assignment、Reservation/Commitment、Operation 与 Receipt。它没有独立状态机，不复制秘密和证据正文。

必测：两个并发 Action 争最后额度仅一个获准；撤权与 Permit 的两个提交顺序；同一资源的 Unknown 阻断后续写；Worker 在 T1/T2 前后分别崩溃；批准后修改 Payload；跨组织同名角色；仅关闭 Exception 而未知仍在；部分成功后补偿再次超时。断言由状态、账本、Outbox、Permit 和 Fake Provider 实际调用计数共同给出。
