# ABH 状态与执行契约规范

> 版本：1.2 · 规范性设计源 · Owner：Contract Maintainer + 各状态 Owner
>
> 范围：ABH 通用持久状态；领域对象状态由 Domain Pack 自有契约定义。
>
> 下列枚举是生成机器 State Registry 的输入；模块只引用本文件，不复制另一套状态图。

## 1. 表达规则

状态表示控制器下一步可做什么；Outcome 表示已知结果；Blocker、Error 和期限是正交字段。UI 显示“未知”不能把 Unknown 当成可安全重试的失败。

每次迁移使用 `aggregateId + expectedVersion` CAS，保存 commandRef、evidenceRefs、actorRef、from/to、reasonCode、committedAt，并在同事务提交 Outbox/Audit。未列出的迁移拒绝；终态不原地重新开始，重做创建新对象并引用原对象。

状态检查与副作用之间存在远端不可原子边界；本规范保证内部提交与 Dispatch 资格可追踪，不能承诺外部 exactly-once。

## 2. Mission

Owner：Mission Controller。生命周期枚举：Draft、Active、Paused、Blocked、Completed、Cancelled。领域阶段使用 `businessStageRef`，不把 Campaign 状态映射成 Mission 状态。

| 迁移 | Command / 证据 |
|---|---|
| Draft → Active | ActivateMission；Goal/成功与停止条件、Workflow、责任与 MissionAuthority 有效 |
| Draft → Cancelled | CancelMission；合法发起者 |
| Active → Paused | PauseMission；持久 stopEpoch，停止新任务 |
| Active → Blocked | BlockMission；无法自动解除的 Blocker Ref |
| Paused → Active | ResumeMission；无强制 Blocker，原阶段和固定版本仍有效，重验授权 |
| Blocked → Active | ResolveBlocker；全部强制 Blocker 消失且人工 pauseRequested=false |
| Blocked → Paused | ResolveBlocker 后仍有人类暂停要求 |
| Active / Paused / Blocked → Cancelled | CancelMission；不删除既有外部效果，保留清理/对账任务 |
| Active → Completed | CloseMission；成功条件证据或登记的正常终止结果；无强制未决副作用 |

Paused 与 Blocked 均保留业务阶段。取消可以在运行期提交，但 Action/Commitment 不随之消失；对账和止损使用独立 Service 权限继续。若已派发 Operation 未决，Mission 可 Cancelled，但 `cleanupStatus=Pending` 明示；不能将取消显示成撤回全部外部效果。

PauseMission 在 Blocked 时保持 Blocked、设置 pauseRequested=true 并提升 stopEpoch；重复暂停幂等。新强制 Blocker 在 Paused 时只追加 Blocker，恢复前必须解决；Active → Blocked 同时提升 stopEpoch。ResumeMission 不能清除未解决的 Blocker。

## 3. Run、Task 与 Invocation

| 对象 | 枚举 | Owner |
|---|---|---|
| Run | Queued、Running、Waiting、Paused、Completed、Failed、Cancelled | Run Orchestrator |
| Task | Pending、Ready、Running、Waiting、Verifying、Succeeded、Failed、Skipped、Cancelled | Run Orchestrator |
| Invocation | Created、Running、Completed、Failed、Cancelled | Run Orchestrator；Adapter 只返回观察 |
| Verification Report | 不可变；verdict=Pass、Reject、NeedsResponsibility、Inconclusive | Verification |

Run：Queued → Running/Paused/Failed/Cancelled；Running → Waiting/Paused/Completed/Failed/Cancelled；Waiting → Running/Paused/Failed/Cancelled；Paused → Queued/Failed/Cancelled。Waiting 保存 waitType/ref/deadline，恢复必须经 Mission Controller 的唤醒 Command。Task 节点推进发生在同一 Run 内，不为每个节点新增 Mission Trigger。

Task：Pending → Ready/Skipped/Cancelled；Ready → Running/Failed/Cancelled；Running → Waiting/Verifying/Failed/Cancelled；Waiting → Ready/Verifying/Failed/Cancelled；Verifying → Succeeded/Waiting/Failed/Cancelled。Ready → Failed 仅用于启动前确定性错误；失败 Task 不原地重跑，创建带 `supersedesTaskRef` 的新节点或经批准 Graph Revision。已完成节点不可删除或改写。

暂停 Run 时停止新 Task、撤销运行中 Invocation 的新调用资格；Running/Verifying 的未完成 Agent Task 进入 Waiting 并记录 resumeDisposition，Pending/Ready 保持状态但不可调度。无副作用且已校验的产物可保留，已有 Domain Receipt 必须查回。恢复后对同一 Task 创建新 Invocation 或进入 Verifying，不重开已终态 Invocation。取消 Run 时所有非终态 Task 可 Cancelled，Invocation 同步请求取消；迟到副作用证据由独立对账处理。

Invocation：Created → Running/Cancelled；Running → Completed/Failed/Cancelled。Completed 只表示 Harness 正常返回，Task 必须经过 Verification 才可 Succeeded。回执迟到仍保留原 Observation，但已取消 Invocation 的输出不能自动合入正式对象。

Run 完成条件为所有 required Task 成功或按预定义 Branch Rule 合法跳过，且所需 Domain Command Receipt/Action Result 已提交。已知领域失败可形成有效业务 Result，但不会把失败 Task 伪装为成功。

## 4. Human Gateway

| 对象 | 枚举 | Owner |
|---|---|---|
| Responsibility Request | Unresolved、Open、Closed、Withdrawn | Human Gateway |
| Decision | Pending、Approved、Rejected、Expired、Superseded、Withdrawn | Human Gateway |
| Responsibility Assignment / Delegation | Active、Revoked、Expired | 各自责任目录 / Control Owner |

Unresolved → Open 需要全部必需责任槽位可路由；Open → Unresolved 用于 Pending 槽位已无合法责任人；Open → Closed 需要全部必需槽位有效通过或已有确定否决；Unresolved/Open → Closed 也允许整体期限到达，此时未决定项过期且无授权效果。Unresolved/Open → Withdrawn 需要原事项取消或替代证据。通知失败不改变 Open。

Decision 仅从 Pending 进入五种终态。Approved 记录被批准对象、版本、影响上界、条件、责任与有效期；改变任一实质内容创建新 Decision 并将旧 Pending 标为 Superseded。Approved 不原地改成 Rejected；撤销后续效力由 Control 撤销其生成的 Grant/Authority，并保留批准历史。

一个 Request 可以有多个 Decision Slot。ANY/ALL/有向先后依赖由冻结 Route 定义；任何 required 槽位否决即不可生成授权。到期只产生 Expired，不产生默认批准。

ANY 槽位由任一合资格候选提交首个有效决定，批准或拒绝均终结该槽位；ALL 槽位对冻结的每个必需责任席位分别创建 Decision，全部批准才通过、任一拒绝即否决。人数和席位由策略冻结，不能因人选离职而静默缩减。Grant Effect 必须消费整个 Request 的有效完成证明，单个 Slot Approved 不提前放行。

## 5. Grant、Snapshot 与资源

| 对象 | 枚举 / 状态 | 迁移 |
|---|---|---|
| Grant / MissionAuthority / ExecutionAuthority | Active、Revoked、Expired | Active → Revoked/Expired；续期按各 Owner 合同创建新版本/新记录，保留旧项，不复活终态 |
| Authorization Snapshot | 不可变记录；有效性动态计算 | 不持久化“永久有效”布尔值 |
| Reservation | Held、Consumed、Committed、Released、Expired | Held → Consumed/Committed/Released/Expired；仅确定未消耗的 Held 可过期释放 |
| Commitment | Open、Closing、Closed | Open → Closing → Closed；Open 内通过追加分录增减；有未结负债不得 Closed |
| Ledger | Open、Frozen、Closed | Open ↔ Frozen；周期/业务结束且无未结 Hold/Commitment、无待核实欠额后可 Closed；历史 Usage 保留 |

Consumed 表示一次性资源已计入 Usage；Committed 表示 Hold 已在同事务转入持续 Commitment，不代表已实际消耗。Usage 更正使用追加分录，不反向改写原 Reservation。Closing 仍允许迟到费用入账，不能因等待超时释放未知负债。以上由 Resource Ledger Owner 提交。

ExecutionAuthority 由 Control 唯一提交，字段与签发见[授权设计第 2.1 节](21-Authorization与Policy详细设计.md#21-独立-action-的-executionauthority)。Active 仍需校验当前时间、来源 Grant/Principal/fence 和冻结上界；来源失效无需等到 Authority 行被异步改状态才阻断。独立 Action 在 Proposed/Validated 可尚未绑定执行 Authority，Validated → Authorized 必须已经绑定有效 ExecutionAuthority；Mission 路径要求有效 MissionAuthority。

## 6. Action：生命周期与 Outcome

Action Engine 拥有生命周期：Proposed、Validated、Authorized、Executing、Reconciling、Closed、Rejected、Expired、Cancelled。

Outcome 枚举：NotStarted、Pending、Unknown、Succeeded、PartiallySucceeded、Failed。外部效果以 Outcome 表达；补偿状态由引用的补偿 Action 表达，不给原 Action 创建第二执行生命周期。

| 生命周期迁移 | 必要条件 |
|---|---|
| Proposed → Validated | Domain 验证、固定业务 Payload/目标版本与完成策略 |
| Proposed / Validated → Rejected | 确定性拒绝，保存原因 |
| Proposed / Validated → Expired / Cancelled | 授权期限或意图失效；无已派发效果 |
| Validated → Authorized | Action 专属 Snapshot、全部预留、审计与 Outbox 同事务成立 |
| Authorized → Validated | Dispatch 前授权失效；未派发任何 Operation；结清本次授权确定无风险的 Hold/Commitment 增量，保留旧 Snapshot |
| Authorized → Executing | 首个 Operation 获得 Dispatch Permit |
| Authorized → Expired / Cancelled | 证明零派发，取消 Plan 和所有未启动 Operation |
| Executing → Reconciling | 已停止新增派发，等待观察/汇总，包括未知结果 |
| Executing / Reconciling → Closed | 所有必需子项结果确定，完成策略已应用 |
| Executing → Executing | 其他可执行 Operation 的推进；仍需版本 CAS |

Proposed/Validated/Authorized/Rejected/Expired/Cancelled 的 Outcome 必须为 NotStarted。Executing/Reconciling 的 Outcome 为 Pending 或 Unknown；已获平台确认且正常处理中为 Pending，发送/效果不明或观察冲突才为 Unknown。Closed 的 Outcome 只允许 Succeeded、PartiallySucceeded、Failed。

已派发后的取消写入 `cancellationRequestedAt` 并停止剩余 Dispatch，生命周期进入 Reconciling；若部分已成功则最终 PartiallySucceeded。原 Action 不进入 Cancelled，避免掩盖既有结果。

Executing 允许新节点及安全重试，Reconciling 仅查回和汇总。进入 Reconciling 时取消全部未派发节点；未知节点后来证实无效果则终结为 Failed，不能再迁回 Pending。Dispatching/Observing → Pending 只在父 Action 仍 Executing、无停止请求且当前授权和重试预算满足时允许。

## 7. Operation、Attempt 与对账

Owner：Operation Controller。Operation 生命周期：Pending、Dispatching、Observing、Closed、Cancelled；Outcome：NotStarted、Pending、Unknown、Succeeded、Failed。

| 迁移 | 证据与结果 |
|---|---|
| Pending → Dispatching | 依赖满足、资源锁/Fencing、实时授权、已持久 Dispatch Permit 与 Attempt |
| Pending → Cancelled | 未派发；取消或依赖失败，Outcome=NotStarted |
| Dispatching → Observing | 已发请求或无法证明未发；Outcome=Pending/Unknown |
| Dispatching → Pending | 可靠传输证据证明零发送且允许再试，重建 Attempt 前再次授权 |
| Observing → Closed | 查回成功/确定无效果失败，Outcome=Succeeded/Failed |
| Observing → Pending | 明确无效果且重试安全，剩余预算/次数足够 |
| Dispatching → Closed | 同步回执足以证明最终效果；仍保存 Reconciliation Record |

合法组合：Pending/Cancelled 仅 NotStarted；Dispatching/Observing 为 Pending 或 Unknown；Closed 为 Succeeded 或 Failed。证明无效果后重新排队将 Outcome 置 NotStarted，但保留全部 Attempt/Receipt。成功意指该原生变更的完成条件成立；具有独立部分结果的响应必须预先拆分节点。

每个 Operation 对应一个 Connection/账户与一个可独立判断的原生变更；批量业务拆成多个 Operation。V1 不合并有独立结果的 Operation 为一个不可判定批量请求。

Attempt 是不可变调用身份，执行状态 Created、Sent、Responded、TransportFailed、Interrupted；观察以追加记录保存，Operation Outcome 不能由 Attempt 的错误状态直接推导。Sent 前崩溃但无法证明零发送时按 Unknown 处理。

Receipt 和 Reconciliation Record 不可变。Reconciliation verdict 为 ConfirmedSuccess、ConfirmedNoEffect、Pending、Ambiguous、Conflicting。只有前两种可使 Operation 终结；超过窗口转正式 Exception，但 Operation 仍 Observing/Unknown，后台只读查回继续按受限计划执行。人工关闭通知不等于证实外部效果。

父 Action 汇总顺序：存在 Unknown → 保持未决；存在 Pending/运行中 → 继续等待；全部 required Operation 成功 → Succeeded；成功与确定失败/取消并存 → PartiallySucceeded；无成功且所有结果确定 → Failed。可选项未完成仅在其尚未派发且完成策略明确允许时忽略；已派发的可选项也必须查回。空 Plan 不得 Authorized。

补偿为新 Action，字段 `compensatesOperationRefs` 指向原子操作；原 Receipt、费用与结果不可改写。补偿效果未知时按相同流程处理。

## 8. 学习、能力与 Pack

| 对象 | 枚举 / 迁移 | Owner |
|---|---|---|
| Capability Candidate | Draft → Evaluating → Eligible / Rejected；Draft / Evaluating / Eligible 可 Withdrawn | Evaluation & Learning；撤回停止新评测，保留已有证据 |
| Gate Artifact | 不可变 verdict：Pass / Fail / Inconclusive | Evaluation & Learning 的独立评测职责；引用 Verification Report，不与其共享写权 |
| Release | Draft → Ready；Draft / Ready → Retired / Revoked | Capability Release Controller；有安全撤回的版本不能新分配 |
| Assignment | Shadow / Canary / Active / Paused / Retired | Capability Release Controller |
| Installed Pack | Staged、Enabled、Suspended、Retired | Pack Loader |
| Definition Version | 不可变；是否可选由 Pack/Release 决定 | Definition Registry |
| Artifact | Staged → Available / Quarantined / Tombstoned；Available → Quarantined / Tombstoned；Quarantined → Available / Tombstoned | Artifact Store；解除隔离必须重新扫描、验 Hash/用途，Tombstoned 终态 |

Assignment：Shadow → Canary/Paused/Retired；Canary → Active/Paused/Retired；Active → Paused/Retired；Paused → 原模式仅在新 Gate 与当前授权均满足时恢复。Assignment 的比例变化是新 revision，不改历史分桶；常规替换后旧 Run 绑定仍可有效，紧急撤回必须显式撤销其执行资格。

Release Ready 只表示可供分配；首次静态基线也需经过安装与配置验证。安全发布的 Mandatory Policy 与 Evaluation Profile 是独立不可变版本，不属于该 Assignment 状态机。

Pack：Staged → Enabled/Retired；Enabled → Suspended/Retired；Suspended → Enabled/Retired 需重新验 Trust 与兼容性。有运行中引用时保留用于安全读取和查回，禁用不能删除原适配代码。Artifact 只有 Available 可被授权读取；Quarantined 不进入模型上下文；Tombstoned 拒绝读取。

Knowledge 的 Candidate → Provisional → Validated → Superseded/Expired 是领域主张协议，由 Domain Knowledge Owner 实现；ABH 只要求 Gate、Scope、来源与失效引用，不创建跨领域统一 Knowledge 内容表。

## 9. 一致性验收

State Registry 为每条迁移提供 Owner、输入、守卫、事务效果、事件和终态约束；生成 OpenAPI 枚举、TypeScript、数据库 CHECK 及穷尽测试。重复命令保持结果，迟到消息不得让终态倒退。迁移表新增状态必须同时提供前端降级与数据库兼容策略。

必测组合：Mission 取消而 Operation 未知；Run 完成但 Task 未验证；Approved Decision 已撤权；授权后未派发的过期；部分成功后补偿失败；未知可选 Operation；暂停 Canary 上旧 Run；Pack 禁用但对账尚未完成。每种组合必须从 API 和 Audit 可观察，不能靠开发者手动改库解除。

## 10. 辅助运行状态

下列状态用于技术工作和权限有效性，统一注册在同一 State Registry，不升级为用户业务对象，也不替代 Action Outcome。

| 类型与使用者 | 枚举及迁移 | Owner / 终态含义 |
|---|---|---|
| AccessRecord：Membership、Workspace、Principal、Binding、Secret Lease、Takeover | Active → Revoked / Expired；新有效期或授权创建新版本 | 各目录/能力 Owner；检查当前 epoch 和 validUntil，不仅看 status |
| JobProgress：评测、导出导入、生命周期清理、安装步骤、隔离工作 | Pending → Running → Waiting / Succeeded / Failed / Cancelled；Waiting → Running / Failed / Cancelled | 对应业务 Owner 保存 progressRef，Durable 管投递；重试保留累计预算，终态重做新 Job |
| Durable Wait | Pending → Succeeded / Cancelled；重复信号或截止唤醒保持原结果 | Durable Execution；Succeeded 仅表示一次唤醒已入可靠 Outbox，条件是否满足由 Owner 判断 |
| External Observation | Received → Normalized / Quarantined；Quarantined → Normalized 需受信规则重验 | Ingress；Normalized 只表示合法观察，领域提交由 Domain Owner 决定 |
| ModelCall / ToolCall | Prepared → InFlight / Failed / Cancelled；InFlight → Completed / Incomplete / Failed / Cancelled | 对应 Gateway；只有完整校验输出才 Completed；Incomplete 不释放未知费用，也不证明外部业务结果 |
| Decision Effect | Pending → Applied / Blocked；Blocked → Applied / Abandoned 需重新验证；Pending → Abandoned 需正式撤回 | Human Gateway 记录目标 Owner Receipt；Applied 仅表示对应 Command 已提交 |
| Mission cleanupStatus | None / Pending / Complete | 从取消后遗留 Operation/资源责任推导的只读投影；不另设可手动关闭的状态 |

AccessRecord 到期以服务器时间确定，后台状态标记尚未更新时也必须拒绝使用。JobProgress 的 Succeeded 只表示该技术工作完成，业务成败与 Unknown 仍从源 Owner 读取。Model/Tool 在 Prepared 取消可直接 Cancelled；InFlight 取消若不能证明零计费/零效果则 Incomplete，由费用/Operation 继续查回。各模块引用 `statusRef` 时必须指向这里的类型或前述专属类型，禁止持久化无枚举约束的自由字符串。

JobProgress 还允许 Pending → Cancelled/Failed；错误与取消必须有正式依据。Model/Tool 的产物终态与费用结算分开，晚到用量追加账本证据，不重开调用。Artifact、External Observation 和辅助状态均进入生成的迁移测试。
